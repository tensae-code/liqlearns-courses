# Security When the System Fails

## Do it first

Attackers are not the only enemy: machines fail on their own — a disk dies, the power cuts, a program corrupts its own store. Laos's Grade 10 security chapter gives system failure its own security section. This lesson plans for the bad day.

## Sub lesson 1 — What system failure threatens

A **system failure** is the machine or its software **stopping, breaking or working wrongly** without any attacker: a **failed disk** taking its only copy of the data, a **power cut** in the middle of writing, a **faulty program** corrupting what it touches, an **overheated or worn part** ending a working day forever. The security loss is the chapter's own triad broken from inside — data **lost** (availability), data **damaged** (integrity) — and it is certain in a way attacks are not: every disk fails eventually, so the question is never if, but whether the failure was prepared for.

## Sub lesson 2 — The defences — copies, power and recovery

Security against failure is built before it happens. **Backups** — copies of the data kept apart and kept current — are the first defence, and they count only if **restoring from them has been practised**. **Uninterruptible power (a UPS)** carries the machine through a cut long enough to close its work cleanly. **Keeping the system maintained** — space free, parts sound, software in order — lowers the failure's chances; and a written **recovery order** (what is restarted, in what order, by whom) turns the bad day from panic into procedure. Laos places the section among its security measures because failure is a security event: the data does not care whether a thief or a dead disk took it.
