## Sub lessons
The parts of this lesson, in order — the list the learner sees from the start, locked ahead, each opening when the one before it is proved:

1. **The prototype — screens you can try** — A **screen prototype** is a **working rough version** of the designed screens: the windows, fields, buttons and messages in their places, responding as the design says (in Malaysia's course, built with Java in **NetBeans**, the chapter's tool). It is deliberately **not** the finished system: the database, the full workings and the polish are left out. What the prototype must keep is everything the **interaction** depends on — layout, order, wording, what happens on each click — because that is what it exists to test.
2. **Rough on purpose — cheap to change** — The prototype's roughness is its virtue: built in hours, it can be **changed in minutes** when evaluation condemns a screen — and evaluation will. Malaysia's rule is to prototype **before** building the system behind the screens, because moving a button on a prototype costs a drag, while moving it in a finished system costs a rebuild. The prototype is thrown into the loop the process taught: users try it, findings land, the prototype changes, users try again. A prototype nobody is allowed to criticise is a finished system wearing a false name — and priced like one.
