# Documenting Database Work

## Do it first

A database that only its maker understands is unfinished work. Malaysia's database chapter closes with documentation: the written record of what was built and why. In this lesson you learn what a database document holds — and what it is for.

## Sub lesson 1 — What the document holds

Database **documentation** records the build in words and diagrams: the **need** the database answers; the **design** — entities, the ERD, the tables with their keys and relationships; the **objects built** — tables, forms, queries, reports, macros — with what each one does; and the **tests** made, with their results. It is written as the work goes, not reconstructed afterwards: a document written from memory at the end is a story, and the difference shows the first time it disagrees with the database.

## Sub lesson 2 — What documentation is for

The document serves three readers: the **checker**, who verifies the work against the need without rebuilding it; the **user**, who learns from it how the system is meant to be used; and the **future maker** — often the same person, months later — who must change the database without breaking it. Malaysia's standard is practical: a competent stranger, given the database and its document, should be able to say what every object is for and where a named fact lives. Documentation is not the work's decoration; it is the part that makes the work outlast its maker's memory.
