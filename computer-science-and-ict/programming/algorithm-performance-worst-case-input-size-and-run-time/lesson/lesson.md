# Algorithm Performance — Worst Case, Input Size and Run Time

## Do it first

Two sortings both 'work'. One finishes the class list before the bell; the other would still be running at lunch. Performance is the lesson that tells them apart in advance.

## Sub lesson 1 — Input size and run time

Performance is measured against the **input size** — how much data the algorithm is given (the list's length, the table's rows) — because the same algorithm's **execution time grows with it**. The honest measure is not one stopwatch reading: it is the **shape of growth** — double the input and the time may double, or quadruple, and that difference, not the machine's speed, is the algorithm's efficiency (αποδοτικότητα) the chapter names.

## Sub lesson 2 — The worst case — judging by the hardest honest input

The chapter's discipline: judge an algorithm by its **worst case** — the allowed input that makes it work hardest — because a promise that holds in the worst case holds always, while an average brag can hide a disaster (searching for the name that stands last, sorting the list that arrives in reverse). Worst case, input size and run time together give the exam's performance judgement: *for n values, in the worst case, the work grows like this* — a sentence that can be written before any machine is switched on.
