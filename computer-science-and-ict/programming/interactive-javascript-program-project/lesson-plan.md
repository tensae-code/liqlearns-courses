# Lesson plan — Interactive JavaScript Program — Project

**Course:** Computer Science and ICT · **Title:** Programming · **Lesson:** Interactive JavaScript Program — Project
**Place in the curriculum:** ICT expansion — Malaysia (2026-11-14) — in the title Programming on the ICT course ladder (TITLES.md). Built new from Malaysia's student books (Kementerian Pendidikan Malaysia), because no existing lesson in the course covers this thing as its own lesson — the live tree and live lesson content were checked for the slug and for near matches before building.
**The one thing this lesson teaches:** A project program that combines client-side scripting structures — data, control, functions and arrays — into one interactive JavaScript program that answers its user (Malaysia, Tingkatan 5)
**This lesson's own level:** It stands on the earlier lessons of its title and on the book's own order — it follows the book's lessons in sequence, so its neighbours in the book are its natural companions. It stands alone for a learner landing on it directly.

A lesson plan also says **what goes on top of the lesson**: at the exact places marked below, the lesson page carries an add-on — an image, a GIF, a video, an audio. Every slot is written as **"a picture of …" in words, plus one little line saying what the student does with it**. The words carry the picture while the course is built and while the AI learns from the books; on the website the real add-on is dropped into that slot and the little explanation stays as the student's guide. GIFs come first where a thing must be shown moving — a GIF here is 1–2 seconds.

## Sub lessons
The parts of this lesson, in order — the list the learner sees from the start, locked ahead, each opening when the one before it is proved:

1. **The brief — a program that answers** — The project program is **interactive**: it **takes input** from its user (typed values, choices, clicks), **processes** it with the chapter's structures, and **answers** on the page — a quiz that marks itself, a converter that converts, a marks tool that bands and totals. The brief is fixed before coding: the user, the inputs, the processing, the answers — because an interactive program is a **conversation**, and a conversation is designed from both sides, not discovered by typing code.
2. **Building with the whole chapter** — The build **combines**: variables and constants hold the state; **if…else** judges the answers; **loops over arrays** carry the lists (questions, marks, items); **functions** each do one job (ask, check, report); the **standard library** is called for what it already does. The program is tested as a conversation — right answers, wrong answers, empty answers, answers at the edges — because a user will send all of them. Malaysia's project standard is the chapter in one artefact: if any structure from the chapter is missing, the brief usually shows where it belonged.

Gate pool: all questions of the sub lesson — no hardness ranking is written in questions/, so the sub lesson's whole question set is the gate pool.
