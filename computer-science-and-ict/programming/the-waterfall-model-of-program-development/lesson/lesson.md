# The Waterfall Model of Program Development

## Do it first

A program of any size is not written; it is developed — through stages, in order, like water falling step to step and never flowing back up. The waterfall is the oldest named way of organising that development, and the models lesson's one-direction model with its name and stages filled in.

## Sub lesson 1 — The stages — analysis to implementation

The waterfall falls through stages. **Analysis**: what problem, exactly, must the program solve, and what will count as its answer? **Design**: the algorithm, the data, the shape of the solution — planned before any code. **Coding**: the design written in a real language. **Testing**: the program tried against known answers and hostile inputs. **Debugging**: the faults testing found, located and removed — testing shows the fault's presence; debugging finds its home. Then **implementation**: the program put to work in its real place, with its real users.

## Sub lesson 2 — Maintenance — and the waterfall's character

The last stage outlasts all others: **maintenance** — the program kept true as the world changes around it: new rules, new needs, faults that only real use reveals. Most of a program's life is maintenance, which is why the good-structure lesson's readability is an economic virtue, not a taste. The waterfall's character is its order: each stage **completed and checked before the next begins**, because a fault found one stage down costs ten times the same fault found in its home stage. Later models bend this order; the waterfall remains the map every developer must be able to draw first.
