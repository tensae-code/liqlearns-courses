# Code Review With a Checklist — short answer

Answer in a short sentence of your own.

**1. (Sub lesson 1) What is code review?**
**Answer: Another programmer reads code before it is accepted, looking for faults, risks and unreadable places**

**2. (Sub lesson 1) Why can't the writer review their own code as well?**
**Answer: The writer reads what they meant, not what they wrote — the reviewer reads what is actually there**

**3. (Sub lesson 1) What three things does the reviewer hunt?**
**Answer: Faults, risks, and unreadable places**

**4. (Sub lesson 1) Where does Armenia teach code review?**
**Answer: Grade 10, Lesson 21 — 'Code review and the checklist'**

**5. (Sub lesson 1) What lessons stand either side of it in the book?**
**Answer: Readable code before it (Lesson 19–20 area) and program debugging after it (Lesson 22)**

**6. (Sub lesson 2) Why use a checklist at all?**
**Answer: It makes review complete instead of impressionistic — nothing depends on the reviewer's mood or memory**

**7. (Sub lesson 2) Name the four sections of a good checklist.**
**Answer: Correctness, readability, safety, and tests**

**8. (Sub lesson 2) What form is each checklist item?**
**Answer: A yes/no question, answerable from the code**

**9. (Sub lesson 2) How does the checklist learn?**
**Answer: It is revised whenever a real fault escapes review — the miss becomes a new item**

**10. (Sub lesson 2) Name two correctness items.**
**Answer: Boundaries checked; empty cases handled (also: division by zero impossible)**
