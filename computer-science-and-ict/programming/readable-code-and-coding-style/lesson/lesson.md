# Readable Code and Coding Style

## Do it first

Code is read far more often than it is written. This lesson learns to write code that can be read.

## Sub lesson 1 — What makes code readable — names and layout

Code is **readable** when a competent reader can say what each part does without detective work. The two great tools are **names** and **layout**: names that say what a variable holds and what a function does (`total_marks`, not `tm`; `find_largest`, not `f2`), and layout that shows the structure — consistent **indentation** for what sits inside what, blank lines between ideas, one idea per line. Armenia's Grade 10 book gives readable code its own lesson (Lesson 19) inside the 'Programs and their quality features' theme: readability is treated as a quality, not a taste.

## Sub lesson 2 — Coding style — one way, kept everywhere

A **coding style** is a team's agreed set of readability rules: how names are shaped (camelCase or snake_case), where braces sit, how long a line may be, how comments are written. No style is magic; the value is **consistency** — a reader who learns the rules once can read the whole program at speed, and differences stand out where they mean something. Styles are kept by agreement, by review (the code-review lesson), and by tools that format automatically.
