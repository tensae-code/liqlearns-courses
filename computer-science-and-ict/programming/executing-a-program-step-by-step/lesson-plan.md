## Sub lessons
The parts of this lesson, in order — the list the learner sees from the start, locked ahead, each opening when the one before it is proved:

1. **One instruction, one state** — **Executing** a program means carrying out its instructions **in order**, each one changing the **state** — where things are, what values hold. The séance executes the class's first Square CT program **together (ensemble)**: one voice reads the instruction, hands perform it, another voice states the resulting state before anyone may read on. The discipline — no skipping, no assuming — is the machine's own, practised by people.
2. **Why execute by hand first** — Hand execution is the programmer's microscope: it shows **what the program actually says**, as opposed to what its writer meant — the gap where bugs live. A class that has executed together can predict a program's behaviour before running it, and when the machine later surprises them, they can replay the execution to find the step where paper and machine part ways. Prediction first, machine second: that order is the séance's whole gift.

## The run of the lesson (in order)
1. **Do it first** — A program lies written on the board. Nobody presses run. Instead, the class will BE the machine: read one instruction, do exactly that, say the new state aloud. Before reading on, guess which instruction will cause the argument. (lesson/lesson.md).
2. **The explanation** — the lesson text in lesson/lesson.md, in its parts in order.
   - ADD IMAGE: a picture of one instruction, one state as the lesson describes it — the student studies the picture and names what each part shows.

   - ADD AUDIO: a voice reading the lesson's key names and definitions aloud, in the order the lesson gives them — the student listens once through, then reads the same lines aloud along with the voice. (Audio is a described slot in this build; no audio file is made.)
