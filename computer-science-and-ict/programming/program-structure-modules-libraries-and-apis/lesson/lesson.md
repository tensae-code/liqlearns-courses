# Program Structure — Modules, Libraries and APIs

## Do it first

Big programs are not written as one block. This lesson learns how they are divided — and how the pieces agree to work together.

## Sub lesson 1 — Modules and libraries — dividing and supplying

A program of any size is divided into **modules**: named parts, each with one job, each hiding its insides and showing a small surface to the rest. Ready modules written by others are gathered into **libraries** — collections a programmer imports instead of inventing (maths libraries, graphics libraries, a school system's date library). Armenia's Grade 11 programme names program structure among its outcomes: the guide's programme (p. 44) expects learners to know how a program is built from modules, libraries and APIs. (This lesson stands on that guide evidence — see sources.)

In your mind's eye: modules and libraries — dividing and supplying.

## Sub lesson 2 — APIs — the agreement between parts

An **API** (application programming interface) is the written agreement at a module's or service's surface: the names of the operations offered, what each needs, and what each returns. Callers promise to ask only through the API; makers promise the insides may change while the API holds. That promise is what lets a library be improved, a school system be rebuilt underneath its screens, and a map service serve a thousand programs it has never seen.

In your mind's eye: aPIs — the agreement between parts.
