# What Makes a Good Program — Structure

## Do it first

Two programs give the same right answer. One can be read by its own author a month later; the other defeats even them. The chapter has taught how to write programs; this short lesson teaches how to judge them — the difference between a program that merely runs and a program that is good.

## Sub lesson 1 — Readable — and always ending

A good program is **readable**: names that mean, structure that shows, comments where the thinking is dense — because programs are read by people far more than they are run by machines. And it **ends**: no **endless loop** waits inside it — every repeat carries the change that brings its condition false, tested in the mind for the inputs that might starve it. A program that might hang has not finished being written, however beautiful its output today.

In your mind's eye: readable — and always ending.

## Sub lesson 2 — Precise answers — and memory respected

A good program gives a **precise final answer**: not approximately, not sometimes — the exact result the problem asked, for the whole range of honest inputs, with the dishonest ones refused as the calculator lesson designed. And it is **efficient with memory**: variables sized to their job, no arrays of a million for a class of thirty, no copies kept from laziness — memory is the machine's shared purse, and the good program spends it like a guest, not an owner. Four tests — readable, ending, precise, frugal — one program, judged whole.
